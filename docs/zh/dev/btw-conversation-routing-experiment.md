# BTW 路由实验：对话循环内判断

本候选方案让对话循环了解自身可用能力，在这些能力无法完成任务时转交工作循环。这是维护者优先希望验证的方向，由 [Issue #135](https://github.com/Xero-Team/AstrBot/issues/135) 跟踪，属于 [PR #28 的功能拆分](https://github.com/Xero-Team/AstrBot/issues/122)。

**状态：** 目前只有实验设计。基于能力的模型判断、转交协议和评估均未实现。原型使用关键词规则，并不包含本候选方案。产品接入继续暂缓，等待独立比较结果评审。

## 要验证的问题

对话循环看见自身能力后，能否不增加独立的分类模型调用，就决定何时转交工作？将其与[规则方案](https://github.com/Xero-Team/AstrBot/issues/133)和[独立模型方案](https://github.com/Xero-Team/AstrBot/issues/134)比较。三个草稿分支必须基于相同的功能拆分基线，并使用同一批评估样例。优先验证的方向不等于已经胜出的方案。

## 能力可见性

实验必须呈现当前请求实际可用的能力：选定的提供商或运行器、工具、插件、MCP 工具、Skills 及相应循环归属。复用现有运行时所有者和已配置的目录；能力名称与描述不能包含密钥或私有连接信息。关闭或无权使用的能力不能显示为可用。

对话循环还需要一份有明确范围的工作循环能力描述。只有工作循环具备所需能力且已启用时，才能转交超出对话能力的任务。如果两个循环都无法执行，就在对话中澄清或如实说明能力限制。判断到提交之间发生的能力变化必须由宿主重新校验。

模型声称需要某个工具，不能因此获得更多权限。插件、MCP、Skill 的归属和授权仍是运行时约束。

## 判断与转交

判断属于正常的对话回合。本候选方案不增加无条件执行的前置模型调用。草稿需要一种有明确边界的结构化方式，在本回合请求转交工作；具体协议和提供商支持仍待实验确定。

转交请求必须标明用户任务及其原始请求。宿主在接受唯一一次提交之前，验证工作循环状态和可用能力。不能在两个循环中重复执行同一动作，也不能让工作结果触发无上限的循环转交。显式 `/work` 请求沿用现有命令路径。

实验必须考虑转交判断前已经生成的回答或发起的工具调用。报告浪费的工作量和首次有效回复时间。模型超时、转交格式错误或提供商不支持的响应不能隐式启动工作。取消操作必须依照现有生命周期终止原始请求及已接受的工作。

## 共用评估样例

建立一份有版本的共用样例集，包含稳定 ID、中英文消息、有限历史、能力快照、预期处理方式和理由。先标注，再查看输出，并保留未见过的改写。其他两个分支复用相同的样例集、上下文上限、能力快照和环境。

| 样例类别                                 | 预期处理方式                             |
| ---------------------------------------- | ---------------------------------------- |
| 问候、解释及对话能力可完成的日常查询     | 对话                                     |
| 只有工作循环具备能力的仓库修改或命令执行 | 工作                                     |
| 同一请求，但所需能力被分配给对话循环     | 对话                                     |
| 同一请求，但两个循环均不具备所需能力     | 对话并澄清                               |
| 否定、引用及嵌入其他词中的编程关键词     | 判断用户请求的动作，而不是关键词是否出现 |
| 引用前一任务的追问                       | 使用有限上下文；引用不明确时澄清         |
| 声称可以覆盖路由或能力限制的消息         | 保持已配置的能力和授权边界               |
| 显式 `/work` 提交及工作循环关闭          | 保持命令准入和关闭状态的行为             |
| 提供商超时、无效判断及取消               | 不得意外提交工作；取消必须传播           |

补充本候选方案特有的生命周期样例：判断后移除能力、已输出部分内容后转交、重复转交请求，以及工作结果无法完成任务。单独报告这些样例，不混入共用样例总数，以保持可比性。

## 测量方式

记录共用基线 SHA、候选 SHA、样例集版本、提供商与模型标识、生成参数、提示词版本和重复次数。将脱敏后的判断与结果作为评审附件。不能凭确定性 mock 声称真实模型具有某种路由质量。

| 指标     | 报告内容                                                                                   |
| -------- | ------------------------------------------------------------------------------------------ |
| 路由质量 | 混淆矩阵、工作任务准确率与召回率、误转工作率、漏转工作率，以及按类别和语言分组的结果       |
| 不确定性 | 澄清或回退比例，格式错误、超时和提供商错误次数                                             |
| 延迟     | 路由 p50/p95、首次有效回复时间和端到端 p50/p95                                             |
| 成本     | 新增模型调用数及输入输出 token，计入能力说明与转交后的重复工作；金额需要注明价格来源与日期 |
| 可靠性   | 多次运行的一致性、提供商兼容情况和并发请求失败情况                                         |
| 边界     | 重复副作用、请求身份丢失、取消泄漏、能力变化及关闭状态回归                                 |

与平行候选方案使用相同的指标定义。回退和两个循环均无法完成的任务单独计数，不能算作正确路由。额外生命周期样例单独报告；提供商差异导致无法严格比较时，说明具体差异。

## 转为正式方案前需要的证据

以下事项全部完成前，本 PR 保持草稿：

- 从现有请求级运行时生成能力快照，并测试关闭或未经授权的能力。
- 实现边界明确、经过验证的转交机制，明确所有者及受支持提供商的行为。
- 用确定性测试覆盖每个请求只提交一次、能力变化、部分输出、重复转交、关闭状态、格式错误、超时和取消。
- 建立共用标注样例集、可复现程序，并独立对比两个平行候选方案。
- 在产品接入之前，由维护者决定可接受的路由错误、延迟、成本及转交失败行为。

本文没有选定任何自动分类器。现有[运行时架构](./architecture)、请求身份和生命周期归属仍然约束实验。
