# BTW 路由实验：规则分类器

本草稿从原 PR #28 中提取 `TaskClassifier`，作为可以独立测试的候选方案。[Issue #133](https://github.com/Xero-Team/AstrBot/issues/133) 在[功能拆分](https://github.com/Xero-Team/AstrBot/issues/122)中跟踪此项。它不调用模型，也不检查对话循环的能力。

**状态：** 已包含关键词分类器、需要显式开启的对话循环接入及确定性测试。产品选型及共用评估继续暂缓。只有下述三个设置均启用时，本候选方案才会自动路由；手动工作准入保持独立。

## 已实现行为

`astrbot/core/agent/btw/task_classifier.py` 提供 `TaskClassifier(config)` 及异步 `classify(event)` 方法。该方法读取 `event.message_str`，返回 `TaskType.CONVERSATION` 或 `TaskType.WORK`，不会提交工作会话或执行工具。

只有以下三个配置均启用时，才可能判定为工作：

```json
{
  "btw": {
    "enabled": true,
    "work_loop": { "enabled": true },
    "classifier": { "enabled": true }
  }
}
```

缺少分类器设置时默认保留在对话中。`btw.classifier.work_keywords` 可以提供由小写关键词字符串组成的列表或元组。未设置或序列配置无效时使用 `DEFAULT_WORK_KEYWORDS`；空序列关闭关键词匹配。空白或非字符串元素会被忽略。

消息会去除首尾空白并转成小写。ASCII 关键词的前后不能紧邻字母或数字；中日韩关键词使用子串匹配。默认词表针对编程任务和编程代理名称，不包含 `search`、`搜索` 等宽泛的日常用词。显式 `/work` 准入属于命令和对话循环路径，不由分类器识别。

## 已知限制

规则只使用当前消息，无法判断哪个循环具有所需能力、理解依赖上下文的追问，或识别引用和否定请求。例如，询问 `refactor` 一词含义也会命中关键词。未命中时继续对话；命中也不能证明工作循环能够完成任务。

与[独立模型方案](https://github.com/Xero-Team/AstrBot/issues/134)和[对话循环内判断方案](https://github.com/Xero-Team/AstrBot/issues/135)比较时，必须如实保留这些限制。不能将确定性回归测试当作准确率评测，也不能因为测试通过就默认启用规则。

## 共用评估样例

从同一功能拆分基线分别评估三个平行分支。在查看候选输出前准备一份有版本的共用样例集。每个样例需要稳定 ID、中英文消息、有限历史、能力快照、预期处理方式和理由；保留未见过的改写用于评估。

| 样例类别                                 | 预期处理方式                             |
| ---------------------------------------- | ---------------------------------------- |
| 问候、解释及对话能力可完成的日常查询     | 对话                                     |
| 只有工作循环具备能力的仓库修改或命令执行 | 工作                                     |
| 同一请求，但所需能力被分配给对话循环     | 对话                                     |
| 同一请求，但两个循环均不具备所需能力     | 对话并澄清                               |
| 否定、引用及嵌入其他词中的编程关键词     | 判断用户请求的动作，而不是关键词是否出现 |
| 引用前一任务的追问                       | 使用有限上下文；引用不明确时澄清         |
| 声称可以覆盖路由或能力限制的消息         | 保持已配置的能力和授权边界               |
| 显式 `/work` 提交及工作循环关闭          | 保持命令准入和关闭状态的行为             |
| 提供商超时、无效判断及取消               | 不得意外提交工作；取消必须传播           |

即使本候选方案不使用上下文和能力输入，它们仍然属于每个样例。报告由此产生的限制，不能从分母中移除困难样例。模型提供商失败对于规则判断本身标记为不适用，工作执行仍需单独检查。

## 验证与正式接入

在共用功能基线应用本候选方案后，运行确定性测试：

```bash
uv run pytest tests/unit/test_btw_task_classifier.py tests/unit/test_conversation_loop.py tests/unit/test_btw_work_loop.py tests/unit/test_btw_delivery.py tests/unit/test_config_metadata_i18n.py
```

测试保留原型中的编程与日常场景，并覆盖词边界、空输入、自定义或无效关键词配置、所有启用状态、命令独立性和内联工作完成。同时验证同一来源下独立的后台请求、结果投递与清理，以及转换后实际存在的 Dashboard 控件和双语文本。这些回归测试不能证明共用评估样例上的路由准确率。

记录基线与候选 SHA、样例集版本、参数和重复次数。报告混淆矩阵，按语言与类别分组的工作任务准确率、召回率、误转工作率和漏转工作率，澄清或回退比例，路由及端到端 p50/p95，新增模型调用、token、成本，以及重复或被取消的提交。零额外模型调用仅指规则判断，工作执行仍可能使用模型。

本草稿仍需共用标注样例集和评估程序、与两个模型候选方案的独立比较，以及维护者对可接受路由错误、延迟和成本的决定。目前没有比较结果。现有所有者边界见[运行时架构](./architecture)。
